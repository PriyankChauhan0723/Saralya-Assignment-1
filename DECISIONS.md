# DECISIONS.md: Engineering & Domain Judgment Log

Every architectural, mathematical, and data judgment call made during the design and implementation of the Collections Cohort Scoring Service, documented with explicit reasoning.

---

| # | Decision Topic | Judgment Call Made | Reasoning & Rationale |
|:---:|---|---|---|
| **1** | **Missing Input Data Representation** | Missing numeric fields (`TOTAL_INCOME`, `FOIR`, `LAST_COLL_DATE`) are stored strictly as `null` in DB and `null` in scoring breakdowns, never silently replaced with constants like `0` or `50`. | The spec forbids silent substitution. Treating missing data as `null` preserves semantic truth and allows downstream consumers to differentiate between a zero-income borrower and an unobserved income record. |
| **2** | **Ability Score Weight Rescaling** | When input data or feed columns (`bounce_pressure`, `balance_cover`, `employment_tenure`) are missing, their weights are set to 0.00 and remaining observed feature weights are rescaled so $\sum w_{\text{observed}} = 1.0$. | The legacy card injected 24% arbitrary static noise via placeholder constants. Dynamic rescaling ensures the score reflects 100% of verifiable information without penalizing or artificially boosting accounts. |
| **3** | **FOIR Collinearity Interrogation** | Separated income verification (`income_stability`) from debt-to-income ratio (`emi_burden (FOIR)`) to eliminate double-counting of FOIR. | In the legacy scorecard, deriving income stability from FOIR caused double-weighting of the same underlying variable in the ability score. |
| **4** | **Data Anomaly: `OUTSTANDING > PRINCIPAL`** | Retained true raw financial figures in storage, but clamped the normalized `exposure_ratio` calculation to `0` ($\min(\text{outstanding}, \text{principal})$). | In real MFI operations, penal interest and late fees can cause outstanding balance to exceed original principal. Raw values must be preserved for audit/collection, but normalized scorecard metrics must not produce negative values. |
| **5** | **Deliberate ML Feature Refusal** | Refused to pass `AMOUNT_PAID_30D` (target leak), `PAID_WITHIN_30D` (target label), `MEMBER_NAME` (PII/ID), `LOAN_NO` (ID), and geographic columns (`STATE`/`DISTRICT`) to the Intent model. | `AMOUNT_PAID_30D` is future information unavailable at scoring time. IDs cause overfitting. Geographic exclusion adheres to fair lending practices preventing regional bias against rural districts. |
| **6** | **Train / Test Split Strategy** | Employed an 80/20 Stratified Random Split on `PAID_WITHIN_30D`. | Because the portfolio dump is a cross-sectional snapshot with no multi-period temporal sequence, an out-of-time split is infeasible. Stratification guarantees identical minority class proportions across train and test folds. |
| **7** | **Class Imbalance Treatment** | Applied Balanced Class Weighting ($w_{\text{class}} = \frac{N}{2 \times N_{\text{class}}}$) during logistic regression training. | The dataset exhibits a 76.3% positive / 23.7% default class imbalance. Without balanced weighting, standard loss minimization favors the majority class and fails to detect high-risk wilful defaulters. |
| **8** | **Model Deployment Runtime** | Trained and validated the logistic regression model in a dedicated pipeline, exporting coefficients to `src/config/intent_model_weights.json` for native Node.js scoring. | Inference for logistic regression is purely arithmetic ($\sigma(w^T x + b)$). Exporting weights provides $< 0.01\text{ms}$ sub-millisecond execution in Node.js without the operational complexity or latency of maintaining an external Python service. |
| **9** | **Deterministic Scoring & Versioning** | Every calculated score is stamped with `modelVersion` (`"v1.0.0-logistic-l2"`) and uses deterministic floating-point clamping. | Auditability is paramount in regulated Indian financial lending. Re-running the scoring engine over identical loan records guarantees bit-for-bit identical scores and cohort assignments. |
| **10** | **Authentication Strategy** | Adopted header-based API key authentication (`x-api-key: <key>`) with environment-based configuration and test bypass. | Provides a clean, standardized, production-ready security boundary without over-complicating testing or deployment. |
| **11** | **Simulation Engine Immutability** | `POST /v1/score/simulate` clones the base loan in-memory, applies overrides, and recalculates scores without modifying database state. | Collections agents conducting live phone calls need to test "what-if" payment scenarios without polluting operational records. |
